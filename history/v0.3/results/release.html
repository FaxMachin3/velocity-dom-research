What this can establish

Compare specific adapter workloads, inspect regressions and check whether changes replicate. It does not establish a universally fastest frontend framework. The default timing includes state reduction, adapter completion and forced layout; they are not INP or confirmed-paint measurements.

Hover a cell for its median bootstrap interval. JS and Wasm release candidates are highlighted, not designated winners. Small differences and near-zero values may be timer noise.

Startup and delivery

Local ready time includes module loading and Wasm compilation. Compression is calculated; browser delivery was uncompressed. Sizes include fixture and benchmark APIs, without source maps or shared CSS.

Architecture and validation

Prefix/suffix matching, minimal-move LIS reconciliation, direct text-node updates, whole-list clear and conditional focus restoration. The batch-HTML experiment was rejected after regressions. Delegated events are compared with the retained direct-handler clone control.

Twenty workloads include create, replace, append, sparse/full updates, select, swap, remove, clear, filter, sort, reverse, rotate, shuffle, input, click, dashboard and no-op cases. Tests additionally cover randomized edits, identity, focus, escaping and remounts.

Rust/Wasm handles unresolved identity matching; the model, DOM and LIS remain JavaScript. Creation and other prefix/suffix fast paths can bypass the planner, so a lower Wasm-labelled creation time is not evidence that Rust accelerated that operation. The API requires immutable snapshots and unique u32 keys. This is a POC rather than a feature-complete component framework.

Chromium only for timings. Firefox correctness attempt timed out; WebKit, physical mobile devices, WAN loading, SSR/hydration and INP remain unmeasured. Shared-host conditions limit comparisons across sessions. JS heap deltas are not total Wasm/process memory.
